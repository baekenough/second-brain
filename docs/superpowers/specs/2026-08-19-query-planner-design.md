# 검색 계획 에이전트(Query Planner) 설계

**작성일**: 2026-08-19
**대상**: `internal/intent`, `internal/api`(`assembleRetrieval`), `internal/model`(`SearchQuery`), `internal/search`
**상태**: 설계 확정 — 구현 전
**관계**: `2026-08-17-ask-pipeline-design.md`(이하 "파이프라인 명세")의 Stage 1(의도분석)을 **대체**한다. 파이프라인 명세 §5.2의 intent→`SearchQuery` 매핑 표는 본 문서 §3·§4의 `QueryPlan` 계약으로 흡수된다. Stage 2(검색 실행)·Stage 3(종합·배출)의 계약은 변경되지 않는다.
**선행 조건**: 이슈 **#196**(포함 필터가 청크 레인에 미적용) 수정 + `model.SearchQuery` 복수 소스 포함 필터 추가. 둘 다 §5 참조. **선행 조건 미충족 상태에서 이 기능을 배포하면 계획기가 낸 소스 필터가 조용히 무시된다.**

## 1. 개요 — 무엇이 문제인가

현재 Stage 1은 `intent.Classify` 하나다. 동작은 이렇다.

1. 고정 정규식으로 어휘를 맞춰본다 — 전화번호, `오늘`, `어제`, `이번 주`, `지난달`, `YYYY년 M월`.
2. 맞으면 `Kind` **하나**를 정하고 (`temporal` 이면 날짜 범위도 계산한다) 끝낸다.
3. 안 맞으면 LLM을 1회 호출해 `general` 인지 `entity` 인지만 고른다.

그리고 `assembleRetrieval`이 그 `Kind`를 가중치 몇 개로 번역한다 — `KindEntity` → `EntityWeight=1.5`, `KindTemporal` → 날짜 범위 통과 + `Sort="recent"`, `KindExactToken` → `BigmWeight=1.5`.

이 구조의 결함은 정규식의 개수가 아니다. **"이 질문에 답하려면 어떤 문서를 가져와야 하는가"를 추론하는 주체가 파이프라인 어디에도 없다는 것**이다. `Kind` 는 질문을 네 개의 통 중 하나에 넣을 뿐이고, 소스 종류·개수·이유는 아무도 결정하지 않는다.

### 1.1 실측 사례 두 건

**사례 A — 날짜 범위를 계산해놓고 검색 계층이 버렸다.**
"오늘 일정에 대해 알려줘" 는 `todayRe` 에 걸려 `OccurredFrom`/`OccurredTo` 가 정확히 계산됐다. 그런데 검색 계층이 그 범위를 후보 풀 제약이 아니라 정렬 힌트처럼 취급해, 캘린더 문서를 **0건** 검색했다. 캘린더(약 14건)는 SMS(약 18,000건) 대비 네 자릿수 작아서, 창을 걸지 않으면 애초에 후보 집합에 들어오지 못한다. → 수정 완료(PR #197 / #200).

**사례 B — 어휘에 없으면 필터가 통째로 사라진다.**
"내일 일정 알려줘" 는 **`내일` 이 정규식 목록에 없다.** 따라서 `KindTemporal` 이 아니라 LLM 경로로 떨어지고, LLM 경로는 날짜를 아예 산출하지 않으므로 날짜 필터 없는 순수 의미 검색이 된다. 결과로 **3개월 전(5/23~24)의 통화 전사**가 올라왔다. 왜 그게 올라왔냐면 — 그 통화 내용이 "4월 6일 일정 조율" 이었기 때문이다. **의미 공간에서는 "일정"과 정확히 겹친다.** 검색은 자기 기준으로는 옳게 동작했다.

사례 B가 본질이다. 어휘 하나(`내일`)의 부재가 "날짜 필터 없음"으로 조용히 번역되고, 그 다음부터는 어떤 층위도 이상을 감지할 수 없다.

### 1.2 정규식을 하나씩 늘리는 방식이 답이 아닌 이유

`내일` 을 추가하면 그 질문은 고쳐진다. 그리고 "이번 주말", "다음 달 초", "지지난 주", "추석 연휴" 에서 정확히 같은 방식으로 다시 깨진다. 어휘 목록은 자연어를 따라잡지 못하고, 실패는 항상 **조용하다** — 매칭 실패와 "시간 표현이 없는 질문"이 구별되지 않기 때문이다.

## 2. 아키텍처

### 2.1 채택안: 단발 계획기(single-shot planner)

```
질문 1개
   │
   ▼
[계획기]  결정적 경로(정규식 히트)  또는  LLM 1회 호출
   │
   ▼
QueryPlan 1개  ── 화면/로그에 노출 가능
   │
   ▼
검색 1회 (assembleRetrieval → search.Service.Search ×2)
   │
   ▼
Stage 3 종합·배출
```

**반복 없음. 재검색 없음. 도구 호출 루프 없음.**

### 2.2 에이전트 루프를 기각한 이유

| 기준 | 단발 계획기 | 에이전트 루프 |
|------|-------------|---------------|
| 지연 | LLM 정확히 0회 또는 1회 → 예측 가능 | LLM 2~5회 변동 → p99가 통제 불가 |
| 테스트 | 질문→계획의 순수 함수 → 골든셋으로 회귀 테스트(§8) | 매 실행마다 궤적이 달라 회귀 테스트 기준선을 세울 수 없음 |
| 설명 가능성 | 계획 1개를 그대로 사용자에게 보여줌 | "왜 이 문서인가"가 여러 턴에 흩어짐 |
| 실패 반경 | 계획이 틀리면 검색 1회가 틀림 | 루프 중간 실패 시 부분 검색 결과의 정합성 불명 |

`/ask` 는 대화형 SSE 응답이다. 지연 변동은 곧 체감 품질이고, 회귀 테스트 불가는 곧 §8 골든셋 불가다. 이 두 가지가 결정적이었다.

### 2.3 불변식 (EARS)

- 계획기는 질문 1개당 정확히 하나의 `QueryPlan` 을 산출해야 한다.
- 계획기가 LLM 경로를 탈 때, 계획기는 LLM을 **1회만** 호출해야 한다.
- LLM 호출이 실패하거나 시간 초과될 때, 계획기는 `Origin="fallback"` 인 무필터 계획을 산출해야 한다 (§6).
- 계획 실행 결과가 0건일 때, 계획기와 호출자는 범위를 넓혀 재검색해서는 안 된다 (§6.2).
- 계획이 시간 창을 산출할 때, 그 경계는 `internal/timeutil.KST()` 기준으로 해석되어야 한다 (§7).

## 3. 새 계약 — `QueryPlan`

```go
// QueryPlan은 "이 질문에 답하려면 무엇을 가져와야 하는가"의 산출물이다.
// 결정적 경로와 LLM 경로가 모두 이 타입을 산출한다.
type QueryPlan struct {
    // 이벤트 시각 창 [From, To). 둘 다 nil이면 시간 제약 없음.
    // 반열린 구간 규약은 기존 intent 범위 헬퍼와 동일하다.
    OccurredFrom *time.Time
    OccurredTo   *time.Time

    // 검색 대상 소스. 빈 슬라이스 = 전체(제약 없음).
    SourceTypes []model.SourceType

    Limit int

    // 사용자에게 보여줄 한 줄 근거. 예: "내일(8/20) 캘린더만 조회".
    Reason string

    // "deterministic" | "llm" | "fallback"
    Origin string
}
```

### 3.1 `Reason` 과 `Origin` 은 장식이 아니다

지금 검색이 엉뚱한 문서를 가져와도, 원인이 **가중치**인지 **어휘 미스**인지 **필터 부재**인지 구별할 방법이 없다. 사례 B에서 사용자가 본 것은 "3개월 전 통화"뿐이었고, 그게 "내일이 정규식에 없어서 필터가 사라진 결과"라는 사실은 코드를 읽어야만 알 수 있었다.

- `Origin` 은 **어느 경로가 이 계획을 만들었는지**를 고정한다. `fallback` 이 관측치에서 급증하면 LLM 경로 장애이고, `llm` 인데 창이 비어 있으면 프롬프트 문제이며, `deterministic` 인데 창이 틀리면 정규식/시간대 문제다. 세 가지가 서로 다른 대응을 요구하는데, 지금은 셋을 구별할 신호가 없다.
- `Reason` 은 **사용자 쪽 진단 채널**이다. 0건 응답과 함께 "내일(8/20) 캘린더만 조회"를 보여주면 사용자가 즉시 "아 범위가 좁았구나"를 판단한다. 아무 설명 없는 0건은 버그와 구별되지 않는다.

이 두 필드는 §10 관측과 §11 Part D 평가의 입력이기도 하다.

### 3.2 `QueryPlan` 과 기존 `intent.Params` 의 관계

`intent.Params` 의 `Kind`/`EntityName`/`Confidence` 는 **가중치 셰이핑 용도로 유지**한다. 엔티티 부스트와 정확 토큰 넛지는 "무엇을 가져올까"가 아니라 "가져온 것을 어떻게 순위 매길까"의 문제이고, 계획기의 관심사가 아니다.

| 관심사 | 담당 |
|--------|------|
| 어떤 문서가 후보에 들어오는가 (창·소스·개수) | `QueryPlan` (신규) |
| 후보를 어떻게 순위 매기는가 (가중치·정렬) | `intent.Params` (기존 유지) |

`assembleRetrieval` 은 두 입력을 모두 받아 하나의 `model.SearchQuery` 로 합성한다.

## 4. 두 경로, 한 산출물

### 4.1 결정적 경로 (즉시, 무료)

정규식 히트 시 LLM 호출 없이 계획을 만든다.

| 표현 | 상태 | 창 (기준일 2026-08-19 수, KST) |
|------|------|-------------------------------|
| `오늘` | 기존 | [08-19 00:00, 08-20 00:00) |
| `어제` | 기존 | [08-18 00:00, 08-19 00:00) |
| `이번 주` | 기존 | [08-17 00:00, 08-24 00:00) |
| `지난달` | 기존 | [07-01 00:00, 08-01 00:00) |
| `YYYY년 M월` | 기존 | 해당 월 [1일, 익월 1일) |
| **`내일`** | **신규** | [08-20 00:00, 08-21 00:00) |
| **`모레`** | **신규** | [08-21 00:00, 08-22 00:00) |
| **`이번 주말`** | **신규** | [08-22 00:00, 08-24 00:00) (토·일) |
| **`다음 주`** | **신규** | [08-24 00:00, 08-31 00:00) |

신규 4종은 기존 `dayRange`/`weekRange` 헬퍼를 재사용한다. `이번 주말` 은 이번 주 월요일 +5일 ~ +7일이다.

### 4.2 LLM 경로 (나머지 전부)

- 모델: DeepSeek, **추론 비활성화**(`LLM_THINKING=disabled`). 추론을 켜면 토큰 예산이 `reasoning_content` 에 소진되어 본문이 비고, `llm.TruncatedError`(`finish_reason="length"`, 본문 길이 0)로 귀결된다 — 즉 매 호출이 폴백이 된다.
- 예산: 약 750 토큰 (시스템 프롬프트 + 질문 + JSON 응답).
- 인터페이스: 기존 `llm.Completer` (`CompleteWithMessages`)를 그대로 사용한다. 새 인터페이스를 만들지 않는다.
- 프롬프트에 반드시 주입할 것: **KST 기준 현재 시각**(LLM은 "내일"을 스스로 계산할 수 없다), 사용 가능한 `source_type` 열거값, JSON 스키마.
- 응답 파싱은 기존 `extractJSON` 규약(첫 `{` ~ 마지막 `}`)을 재사용한다.

### 4.3 왜 정규식을 남기는가 — 근거는 성능이 아니라 일관성

LLM 경로가 모든 표현을 처리할 수 있는데도 정규식을 남기는 이유는 지연/비용 절감이 **아니다**(그건 부수 효과다).

핵심은 **두 경로가 같은 타입을 산출한다**는 점이다. 지금의 결함은 `오늘` 은 날짜 창을 갖고 `내일` 은 갖지 않는 것 — 즉 경로마다 **산출물의 모양이 다른 것**이었다. 산출물 타입을 `QueryPlan` 하나로 통일하면, 정규식은 "흔한 표현에 대한 캐시"로 격하되고 어느 경로를 타든 하류 동작이 동일해진다. 정규식이 어떤 표현을 놓쳐도 그것은 **지연이 조금 늘어나는 문제**이지 **필터가 사라지는 문제**가 아니게 된다.

같은 이유로 §8 골든셋은 두 경로를 구분하지 않고 하나의 표를 통과시킨다.

## 5. 선행 조건 (구현 착수 전 반드시 해소)

### 5.1 #196 — 포함 필터가 청크 레인에 적용되지 않는다

`internal/search/search.go` 의 `dropExcludedSourceTypes` 는 이름 그대로 **exclude만** 처리한다. 청크 레인(`searchChunksVector` / `searchChunksFTS`)은 쿼리/벡터와 limit만 받으므로 소스 필터를 SQL로 걸 수 없고, 사후 필터링도 exclude 목록만 본다. **`q.SourceType` 포함 필터는 청크 레인에서 통째로 무시된다.**

측정: calendar 14건을 요청한 질의에 타 소스 **6건**이 혼입.

즉 계획기가 `source_types: ["calendar"]` 를 산출해도 **현재 코드베이스에서는 그 지시가 작동하지 않는다.** #196 수정이 이 기능의 선행 조건이다.

> **주의 — 부분적으로 가려진 결함**: 현재 `Search` 는 `windowed := q.OccurredFrom != nil || q.OccurredTo != nil` 일 때 청크 레인을 아예 건너뛴다. 따라서 "내일 일정"처럼 **창 + 소스**를 함께 지정하는 계획은 우연히 정상 동작한다. 그러나 "홍길동과의 통화 내용"처럼 **창 없이 소스만** 지정하는 계획은 청크 레인이 살아 있어 그대로 오염된다. 계획기 도입은 후자 형태의 계획을 처음으로 대량 발생시키므로, #196은 도입과 동시에 노출된다.

### 5.2 `model.SearchQuery` 에 복수 소스 포함 필터가 없다

현재 필드는 단수 `SourceType *SourceType` (nil = 전체)뿐이다. `QueryPlan.SourceTypes` 가 `["calendar", "gmail"]` 처럼 복수를 낼 수 있으므로 스키마 확장이 필요하다.

```go
// 추가 (기존 SourceType은 호환을 위해 유지하거나 마이그레이션)
SourceTypes []SourceType // 빈 슬라이스 = 전체
```

문서 스토어의 SQL 술어(`source_type = $1` → `source_type = ANY($1)`)와 청크 레인의 사후 필터 양쪽을 함께 고쳐야 한다. #196과 같은 코드 경로를 건드리므로 **한 작업으로 묶는 것을 권장**한다.

### 5.3 인사이트 레인과의 충돌 정리

`assembleRetrieval` 은 본검색에 `ExcludeSourceTypes=[insight]` 를 고정으로 넣고, 인사이트검색은 `SourceType=insight` 로 별도 호출한다. `SourceTypes` 도입 시 **include와 exclude가 동시에 insight를 지목하는 상태**가 만들어질 수 있다(계획기가 `source_types:["insight"]` 를 산출하는 경우). 우선순위 규칙을 명시적으로 정할 것 — 권장: 본검색은 계획의 `SourceTypes` 에서 insight를 제거하고, 인사이트 레인만 별도 유지.

## 6. 실패 처리

| 상황 | 동작 |
|------|------|
| LLM 호출 실패 / 타임아웃 / `TruncatedError` | **필터 없는 계획으로 폴백**, `Origin="fallback"`, `Reason` 에 "시간·소스 제약 없이 전체 검색" 기록 |
| LLM 응답이 스키마 위반 (JSON 파싱 실패, 알 수 없는 `source_type`, `To <= From`) | 동일 폴백 |
| 계획 실행 결과 **0건** | **범위를 넓히지 않고 0건이라고 답한다** |

계획기는 `intent.Classify` 와 동일하게 **호출자에게 에러를 표면화하지 않는다**. 모든 실패는 폴백 계획으로 흡수된다.

### 6.1 폴백 계획의 정의

`OccurredFrom=nil, OccurredTo=nil, SourceTypes=[], Limit=기본값, Origin="fallback"`. 즉 현재의 무필터 동작과 정확히 같다. 폴백은 **기능 추가 이전 상태로의 복귀**이지 새로운 실패 모드가 아니다.

### 6.2 0건일 때 조용히 넓히지 않는다

이미 날짜 필터에 적용한 원칙과 같은 원칙이다(`internal/search/search.go`: 창이 걸린 질의에서는 청크 FTS 폴백을 실행하지 않는다 — "오늘 아무 일도 없었다"를 다른 날의 매치 목록으로 바꾸지 않기 위해).

"내일 일정 없습니다"가 정답인데 3개월 전 통화를 보여주는 것이 **현재 상태**다. 계획기의 목적 절반은 이 동작을 없애는 것이다.

> **드러내는 확대는 허용하되(사용자에게 명시), 조용한 확대는 금지.**
>
> 허용 예: 0건 응답 + `Reason` 표시 + "범위를 이번 주로 넓혀 다시 찾을까요?" 제안.
> 금지 예: 0건이면 자동으로 창을 제거하고 재검색해 결과를 그냥 보여주는 것.

## 7. 미래 날짜 — 검색 경로 전 구간 점검 항목

`내일`·`모레`·`다음 주` 는 **미래**다. 캘린더 일정은 대부분 미래인데, 기존 시간 창은 전부 과거 기준(`occurred_at >= now() - interval`)으로 설계·검증되어 왔다. 미래 창은 이 시스템에서 **한 번도 검증된 적이 없는 입력**이다.

구현 시 다음을 각각 확인할 것.

- [ ] **문서 스토어 SQL**: `occurred_at` 술어에 상한/하한 외의 암묵적 `<= now()` 클램프가 없는가.
- [ ] **컬렉터/워커 인덱싱**: 미래 `occurred_at` 문서가 정상 인덱싱·임베딩되는가 (미래 시각을 이상치로 버리는 경로가 없는가).
- [ ] **최신성 워치독**(`FreshnessChecker`): 미래 시각 문서를 "시계 오차"로 오탐하지 않는가.
- [ ] **RRF / 재순위**: `recency` 성격의 점수 항이 `now()` 로부터의 **절대 거리**가 아니라 부호 있는 차이를 쓰고 있지 않은가 (미래 문서가 음수 거리로 강등되지 않는가).
- [ ] **`Sort="recent"` 의 의미**: `model.SearchQuery` 주석상 `recent` 는 **`collected_at` DESC**다. 미래 창에서 이 정렬은 "수집된 순서"이지 "임박한 순서"가 아니다. 미래 창에서는 `occurred_at ASC`(가장 임박한 일정 먼저)가 자연스러운 읽기 순서다 — §12 위험 R3 참조.
- [ ] **`occurred_at IS NULL` 제외 규칙**: 창이 하나라도 설정되면 NULL 행은 전부 제외된다(스토어 규약). 계획기는 창을 지금보다 **훨씬 자주** 산출하므로 이 제외의 영향 범위가 넓어진다 — §12 위험 R2 참조.

## 8. 검증 — 골든셋

질문 → 기대 계획의 표를 고정하고, **결정적 경로든 LLM 경로든 같은 표를 통과해야 한다**(§4.3). 경로별로 별도 기준을 두면 §4.3의 통일 근거가 무너진다.

**기준 시각**: 2026-08-19(수) 10:00 KST. 테스트는 주입 클록(`now func() time.Time`, 기존 `LLMClassifier` 규약)을 사용한다. **컨테이너는 Etc/UTC로 돌아가므로 모든 기대값은 KST 기준으로 적고 `timeutil.KST()` 로 구성한다.** 개발 머신이 KST여서 로컬 테스트만 통과하고 프로덕션에서 9시간 어긋나는 사고가 이미 한 번 있었다.

### 8.1 골든셋 판정 규칙

- `OccurredFrom`/`OccurredTo` 는 **정확 일치**(instant 비교). "대략 맞음"은 불합격 — 사례 A는 9시간 어긋남으로 0건이 났다.
- `SourceTypes` 는 **집합 일치**(순서 무관).
- `Reason` 은 비어 있지 않을 것(내용은 미검증).
- `Origin` 은 결정적 경로 기대 항목(#1~#9)에서 `"deterministic"` 이어야 한다. 나머지는 `"llm"` 또는 `"fallback"` 을 허용한다.
- LLM 경로 실행 시 항목별 판정은 **N회 반복 중 다수결이 아니라 전회 통과**를 요구한다. 흔들리는 계획은 §11 평가에서 잡을 문제가 아니라 프롬프트 결함이다.

### 8.2 골든셋이 커버하지 않는 것

검색 **결과의 품질**은 골든셋의 대상이 아니다. 이 표는 "계획이 맞는가"만 본다. "맞는 계획으로 검색했을 때 좋은 문서가 나오는가"는 §11 Part D의 영역이다.

## 9. 개인정보

**`QueryPlan.Reason` 에는 실명·전화번호 등 개인 식별 정보가 들어갈 수 있다.** LLM이 질문을 요약해 근거를 쓰기 때문이다 — 예: "홍길동과의 통화 기록만 조회". 질문 자체가 개인정보를 담고 있으므로 이는 회피 불가능하다.

따라서 `Reason` 은 **사용자 응답 채널 전용**이며, 다음 규칙을 적용한다.

| 대상 | 정책 |
|------|------|
| SSE 응답 / UI 표시 | `Reason` 전문 표시 허용 (질문 주체 본인에게만 반환됨) |
| 애플리케이션 로그(`slog`) | **`Reason` 전문 기록 금지.** 길이만 기록(`reason_len`) |
| 메트릭 라벨 | **`Reason` 금지**, `Origin`·창 유무·소스 개수 등 저카디널리티 값만 |
| 에러 메시지 | 금지. `llm.TruncatedError` 가 본문 대신 길이만 담는 것과 동일 원칙(#194) |
| 골든셋 픽스처 | 가공 더미만 사용 (본 문서 §8 표 참조: `홍길동`, `010-0000-0000`) |

원문 질문(`RawQuery`)에 대해서도 같은 정책이 이미 적용되어야 한다. 계획기 도입으로 **새로 생기는 노출 지점은 `Reason` 하나**이므로, 구현 시 이 필드의 모든 싱크를 열거해 확인할 것.

## 10. 관측

계획기가 없던 시절에는 "검색이 왜 이 문서를 가져왔는가"에 대한 신호가 없었다. 최소한 다음은 내보낸다.

| 신호 | 타입 | 라벨/필드 | 목적 |
|------|------|-----------|------|
| `query_plan_total` | counter | `origin`(deterministic/llm/fallback) | 폴백 급증 = LLM 경로 장애 |
| `query_plan_llm_duration` | histogram | — | 계획기가 `/ask` 지연에 기여하는 몫 |
| `query_plan_windowed_total` | counter | `has_window`(bool) | 창이 걸리는 비율 추이 |
| `query_plan_source_filtered_total` | counter | `source_count`(0/1/2+) | 소스 필터 사용 빈도, #196 영향 범위 추정 |
| `query_plan_empty_result_total` | counter | `origin`, `has_window` | 0건 응답이 계획 탓인지 데이터 탓인지 분리 |
| 구조화 로그 | — | `origin`, `from`, `to`, `source_types`, `reason_len`, `limit` | 개별 질의 사후 추적 (§9: `Reason` 전문 제외) |

**핵심 알람 후보**: `fallback` 비율이 기준선을 넘으면 계획기가 사실상 꺼진 상태다. 이 경우 기능은 "조용히" 도입 이전 동작으로 되돌아가므로 — 사용자에게는 아무 에러도 보이지 않는다 — 메트릭 없이는 감지 불가능하다.

## 11. Part D(피드백 루프) 연계

`docs/superpowers/plans/2026-08-18-feedback-loop.md` 의 피드백 루프가 붙으면 **계획 품질 자체가 평가 대상**이 된다. `QueryPlan` 은 구조화되어 있고 `Origin`/`Reason` 으로 출처가 표기되므로, 사용자 피드백(👍/👎)을 "생성 품질"과 "계획 품질"로 분해할 수 있다 — 지금은 불가능한 구분이다.

## 12. 미해결 위험

**R1 — #196 수정 없이 배포하면 실패가 조용하다.**
계획기가 `SourceTypes` 를 내고, 청크 레인이 그것을 무시하고, 결과에 타 소스가 섞인다. 사용자에게는 `Reason` 이 "캘린더만 조회"라고 표시되는데 결과는 캘린더가 아니다 — **설명 가능성이 오히려 거짓말이 되는 최악의 형태**다. §5.1의 창 유무에 따른 부분 가림 때문에 QA에서도 놓치기 쉽다. 완화: 골든셋 #11(창 없이 소스만)을 통합 테스트로 승격.

**R2 — 창을 자주 걸수록 `occurred_at IS NULL` 문서가 대량 제외된다.**
스토어 규약상 창이 하나라도 설정되면 `occurred_at IS NULL` 행은 전부 후보에서 빠진다(의도된 설계: `collected_at` 으로 coalesce하면 "수집 시점"이 "발생 시점"으로 둔갑한다). 그런데 코퍼스의 상당 부분이 NULL `occurred_at` 이다. 계획기는 창 산출 빈도를 크게 올리므로, **"필터를 잘 걸었더니 오히려 덜 찾는" 회귀**가 가능하다. 미해결: 소스별 `occurred_at` 채움률을 먼저 측정하지 않으면 이 회귀의 규모를 예측할 수 없다.

**R3 — 미래 창에서 `Sort="recent"` 의 의미가 어긋난다.**
`recent` 는 `collected_at` DESC다. "다음 주 일정"에 대해 이 정렬은 "최근에 수집된 순서"를 주는데, 사용자가 기대하는 것은 "가장 임박한 순서"(`occurred_at` ASC)다. 미래 창 전용 정렬 모드가 필요한지, 아니면 Stage 3에서 재정렬할지 미결.

**R4 — 창 설정 시 청크 레인이 통째로 꺼진다.**
현행 `windowed` 게이트는 창이 있으면 청크 벡터/FTS 레인을 건너뛴다(정당한 이유가 있다 — 청크는 `occurred_at` 을 들고 오지 않아 사후 필터가 불가능하다). 계획기가 창을 자주 걸면 **청크 단위 재현율이 그만큼 자주 사라진다.** 근본 해결은 청크 레인에 이벤트 시각을 전파하는 것이며, 본 설계 범위 밖이다.

**R5 — LLM이 창을 과잉 산출할 수 있다.**
"최근에 받은 메일"(골든셋 #13)처럼 시간 표현이 모호한 질문에서 LLM이 임의의 창(예: 최근 7일)을 만들어낼 유인이 있다. 이는 §6.2가 금지한 "조용한 축소"의 거울상이다. 프롬프트에서 **"명시적 시간 표현이 없으면 창을 비워라"**를 강하게 지시하되, 이 지시의 준수율은 골든셋 #12·#13로만 관측 가능하다.

**R6 — 결정적 경로와 LLM 경로의 불일치가 조용히 생길 수 있다.**
같은 표현을 양쪽이 다르게 해석하면(예: `이번 주말` 을 정규식은 토·일로, LLM은 금·토·일로) 정규식 히트 여부에 따라 답이 달라진다. 골든셋이 두 경로를 같은 표로 검증하므로 **표에 있는 표현에 대해서는** 잡힌다. 표에 없는 표현은 잡히지 않는다.

**R7 — 계획기 지연이 `/ask` p99에 더해진다.**
LLM 경로는 검색 **이전**에 직렬로 들어간다. 결정적 경로 히트율이 낮으면 모든 질의가 +1 LLM 왕복이 된다. 히트율 목표치를 정하지 않았다. §10의 `query_plan_total{origin}` 으로 사후 측정.
